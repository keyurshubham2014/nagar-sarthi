## 1. Objective

A corporator opens a ward and reads a one-page brief in English, Hindi or Marathi and a fair scorecard for each contractor, with every number opening the work orders behind it.

## 2. Scope

### In Scope
- Contractor scorecard screen with fairness notes
- Evidence drill-down from each metric
- Ward brief generated by Claude in three languages

### Out of Scope
- Scorecard maths (TASK-01)
- Translated interface chrome (TASK-07)

## 3. Prerequisites

TASK-02 running. Scorecards present in the audit JSON.

## 4. Dependencies

| Task | Why it is required |
|---|---|

## 5. Technical Context

### 5.1 Requirements Covered

| Req ID | Requirement | Source |
|---|---|---|
| REQ-F-028 | Contractor scorecard screen shows speed, durability, cost and volume, and each number opens its work orders | PRD §5 F3 |
| REQ-F-029 | Ward brief is generated in English, Hindi and Marathi only from audit engine numbers | PRD §5 F7 |

### 5.2 Data Contracts

Not applicable — reads the audit JSON only.

### 5.3 API Contracts

Uses `GET /api/contractors`, `GET /api/wards/:code`. Adds the `brief` feature to `POST /api/claude/brief` with body `{ward_code, language}`; figures come from the server. Adds `GET /api/contractors/:id/work-orders?metric=`.

### 5.4 UI Surfaces & States

Scorecard list and card: default, loading, error, empty, and a not-rated state for small samples with the reason shown. Reuses Saarthee scorecard bar and stat tile. Brief screen: language switch, drafting, drafted, fallback badge.

### 5.5 Permissions & Roles

Intended for corporator and officer roles; citizens see the brief. Enforced in TASK-07.

### 5.6 Assumptions

- ASSUMPTION: the brief is at most 200 words — the organisers' starter prompt uses 120 for a scorecard; a ward brief covers more ground

## 6. Implementation Steps

1. Add the brief prompt on the server with saved fallbacks per language for the demo ward
2. Add the work-orders-by-metric endpoint
3. Copy Saarthee scorecard widgets and adapt them
4. Build the scorecard list and card with fairness notes, strength and improvement
5. Show the not-rated state with its reason
6. Wire each metric to its work order list
7. Build the brief screen with the language switch

## 7. Acceptance Criteria

### 7.1 Behavioral

**AC-1** — Scorecard reads fairly
- **Given** a contractor card
- **When** it is opened
- **Then** speed and durability are shown against the same-method average with one strength and one improvement

**AC-2** — Evidence behind numbers
- **Given** any metric on a card
- **When** it is tapped
- **Then** the work orders behind it are listed

**AC-3** — Small samples
- **Given** a contractor below the minimum sample in a ward
- **When** the card is opened
- **Then** no rating is shown and the reason is stated

**AC-4** — Brief in three languages
- **Given** a ward
- **When** the brief is requested in English, Hindi and Marathi
- **Then** each version is returned and uses only figures from the audit engine

**AC-5** — Brief fallback
- **Given** the Claude call fails
- **When** the brief is requested
- **Then** the saved brief is shown with a fallback badge

### 7.2 Non-Functional Checklist

- [ ] Error states: every failure path renders a recoverable state, no unhandled rejections
- [ ] Loading states: every async surface has a loading representation
- [ ] Empty states: every list or collection surface has a designed empty state
- [ ] Logging: failures logged with context, no secrets or personal data in logs
- [ ] Accessibility: labelled controls, visible focus, adequate contrast
- [ ] Responsive: verified on the Android emulator and at desktop web width
